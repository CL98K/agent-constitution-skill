# 交付报告模板

> 按 `../SKILL.md` §8 汇报结果。依据任务规模精简；自检通过不等于用户接受。状态字段含义见 `../SKILL.md` §7。

## 推荐结构

```text
目标｜<对用户目标的忠实摘要>
改动｜<具体产出及涉及范围>
验收条件｜<逐条列出：判据、状态、证据；未验证则说明原因>
流程自检｜pass / fail / unverified，及相关证据或缺项
未验证｜<检查和原因；无则写无>
风险与遗留｜<事项及影响；无则写无>
用户待决策｜<明确问题；无则写无>
```

标准或团队任务需要时，可逐条对应状态文件中的 `accept`。不要用整体“通过”掩盖单项未验证或失败。命令证据写原命令与实际观察到的结果；未运行命令不得附编造的输出。文档设计走查应标为设计审查，不称为测试。

## 示意例

以下是虚构的报告结构示意，不代表任何检查实际运行：

```text
目标｜修复登录表单邮箱校验
改动｜更新提交校验并补充测试
验收条件｜A1：非法邮箱阻止提交，未验证（尚未运行测试）
流程自检｜unverified；尚未完成实现与回读
未验证｜相关测试、类型检查
风险与遗留｜无已知事项
用户待决策｜无
```

## 完成交付前

- 每条用户验收条件都有状态和证据，或有具体未验证原因。
- 实施完成与用户接受明确区分；不代用户宣布接受。
- 报告范围与实际改动一致，异常和失败不被隐藏。
- 说明未执行项、风险、遗留与需要用户决定的事项。
