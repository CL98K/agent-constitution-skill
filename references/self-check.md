# 交付前自检

按 [主流程](../SKILL.md) §2 选择适用项，记录通过、失败、未验证或不适用及原因。人工核对应说明人工；脚本检查应有实际命令与结果。自检不是用户验收。

## 1. 目标和验证证据

- 目标、约束和范围是否忠实保留用户要求？推导判据是否与用户判据区分？
- 每条判据是否有结果和对应证据？尚未执行、实际失败和设计走查是否分别说明？
- 检查是否验证目标本身？是否误用不相关的构建/测试替代文档、行为或视觉检查？
- 报告是否把成员自报当作已复核、把示例当作实测、把自检当用户验收？
- 是否保留原失败，避免以删断言、禁用测试或缩小检查范围宣称通过？

## 2. 模式与状态（standard/team 适用）

字段和枚举只按 [SKILL.md §7](../SKILL.md#7-状态与日志唯一字段定义源) 核对，模板不另立规则。

- 开工及实质目标/范围/判据变化时，是否在业务步骤前对话输出了标明 S/C/A/N 的 SCAN，并留有规划记录？
- 状态/日志文件身份和安全文件名是否与当前会话匹配？是否避免覆盖其他会话或业务文件？
- 状态字段、类型、唯一判据 ID、时间时区和实际进度是否一致？有解析器时是否实际解析回读，排除时间被转成日期对象、含冒号的列表项被转成映射等类型错误？
- `flow` 是否据实反映流程缺项？是否通过伪造历史补记录？
- `retry_total` 是否与本目标的重派记录一致？普通命令重试有没有误计？
- 目标切换是否保留旧目标和未完成项摘要？追问是否被误当作取消原任务？
- 恢复时是否核对现场而非盲信旧状态？已有继续指令时是否多余重复请求确认？
- `done` 与所有判据结果是否相符？未验证的影响是否公开？

## 3. 写入与协作

- 改动前是否读取相关内容？有并发写者时是否重新核对？
- 实际改动是否服务于用户任务及已授权范围？是否保留他人原有改动？
- 合法缩短是否经过内容核对？是否意外丢掉字段、未完成项或历史？
- 若启用团队：写域、依赖、交接与证据是否明确？最终 diff 与集成结果是否由集成者复核？
- 写域外失败的归属是否有基线或因果证据，而非仅靠排除后变绿？
- 操作失败或未知效果是否在重试前检查？权限拒绝是否被遵守？
- commit、push、发布和清理是否符合用户授权，且实际结果已区分？

## 4. 规范或文档改动适用项

- 主流程、模板和自检是否对同一状态或阈值给出冲突要求？字段 schema 是否以主流程为准？
- 所有本地 Markdown 链接及节号是否存在？索引是否覆盖全部附属文件？
- Skill frontmatter 的名称是否与目录匹配，描述是否说明用途和触发场景？
- 是否留有本机绝对路径、指定 Shell/平台前提、未填写项目参数或失效附录引用？示例路径和明确说明的默认文件名不按硬绑定处理。
- 可复用模板中的填空与示例是否清楚区分？模板占位符不等于交付内容允许留空。
- 示例是否标明示意/未运行？命令的工作目录、参数及前置条件是否足够？
- 文档标题层级、术语、围栏、编码和行尾是否一致？是否有无助于读者的重复？
- 语义规则可为操作和示例提供必要上下文，不要求机械的逐字零重复；判断是否存在多个冲突定义源。

## 5. 结论与补救

可修正的问题先修正，再复查受影响项；无变化的检查不必无限重复。无法运行或无法补证的检查保留“未验证”及原因，实际失败保留失败与影响。

light 不因没有状态文件或团队记录判失败。standard/team 的缺项如实记入 `flow`；交付措辞与 [SKILL.md §8](../SKILL.md#8-交付与结束) 一致。说明未执行项、临时产物处置、风险与下一步，不能替用户写 accepted。
