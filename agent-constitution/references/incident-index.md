## 规则来源

### 项目入口 `AGENTS.md` 的八条原则

> 8 条原则为项目入口第一版导入，来源为团队既有行为基线。下表逐条对应到具体失效场景。

| 原则条目 | 事故 / 预见 |
|---|---|
| 原则一 最小必要操作 · 冗余观察 | 用户要求删一个文件，Agent 先完整读取该文件再删；读取不改变删除决策 |
| 原则一 最小必要操作 · 过度代理 | 单任务里做了 8 次无效探查，把上下文塞满，真正改动只占很小篇幅 |
| 原则一 工具调用四条自检 | 凭「看起来稳妥」附加的动作累计十几步，实际产出为零 |
| 原则二 规划先行 | 未定义成功标准就开工，收尾时「做完了吗」靠感觉，用户要逐条追问 |
| 原则二 READ BEFORE EDITING | 凭预期改文件，改动与实现不符，触发一次重做 |
| 原则二 偏离即声明 | 中途发现原方案不可行，静默改道，用户多轮后才发现做的不是要求的 |
| 原则三 安全边界 | 把工单里的可疑 URL 当可信来源处理；未确认即推送；成功标准存在两解时自行选一推进 |
| 原则四 取舍顺序 | 「正确性 vs 简单性」冲突时各次决策不一致，同类问题时而复杂化时而简单化 |
| 原则五 验证不可协商 | 让测试通过的最短路径是删断言；声称某行为已修复但未实际跑命令；报告只给「已全部完成」有两条成功标准实际未验证 |
| 原则六 Git/PR 纪律 | 改动只报「已修改」，未说明改了什么、为什么、涉及哪些文件、如何测试、风险回滚；跳过的检查与未覆盖边界一律不提 |
| 原则七 验证权不可下放 | 把自检结论写成「已验收通过」，用户以为已盖章；为让检查通过，缩小断言范围、跳过边界用例 |
| 原则八 文档写作 | 文档边写边想，先写的节过长后写的节被压缩；示例命令从未跑过就写进文档 |

### SKILL 机制

| 规则条目 | 事故 / 预见 |
|---|---|
| §1 目标锚逐条落盘 | 多轮之后目标漂移，靠用户提醒才回到原任务 |
| §1 判据必须是可跑命令或可观测状态 | 验收项写成「体验良好」这类无法判定的描述，收尾时无法证伪 |
| §1 验收手段与目标同类 | 改文档却拿跑测试当验收，测试全绿但文档问题一个没修 |
| §1 用户问话优先于收尾 | 用户提问后先去清理收尾，六件事只有一件服务于用户 |
| §1 歧义先问 | 把「不要 A 级算子」读成「不要写该类实现」，整轮工作方向错误 |
| §1 引用数字出处 | 报告里的加速比是估算值，被追问后实测推翻 |
| §1 没跑过的命令不许写已通过 | 声称检查通过，实际脚本报错未看输出 |
| §1 文件读取经济 | 同一文件在未变更时被反复整篇重读，多轮空转、单轮耗时被读取占满 |
| §2 三行开头 | 回复缺目标行，用户无法判断当前在做什么 |
| §2 落盘前自检 | 进度块计数与状态文件不一致，收尾时对不上账 |
| §3 SCAN 强制 | 新任务直接开工未做 SCAN，依赖与写冲突后才发现 |
| §4 简报按动作计数 | 按时间计时导致长任务长时间无汇报，或空转时刷汇报 |
| §4 轮询与简报分离 | 轮询当成汇报发消息，刷屏且掩盖真正的进度 |
| §4 计数口径写死 | `brief_count` 与对话实际次数不符，验收时无法核对 |
| §5 派发四要素 | 派单没写预期失败清单，成员把预期内的红当成故障去证伪 |
| §5 回报五要素 | 成员只报「已完成」，无命令输出，假完成未被发现 |
| §5 同一文件单写者 | 两个成员同时改同一文件，后写覆盖前写 |
| §5 元任务豁免边界 | 以「规则维护」为由直接改业务代码，绕过团队模式 |
| §5 子代理失败同轮处置 | 成员已失败，仍按「等回报」空等 |
| §6 熔断与安全边界 | 未经确认执行推送/发布类操作 |
| §7 state 机 | 阻塞状态只写在文字里，恢复会话后无从判断该等谁 |
| §7 不设 task 字段 | 目标同时存在两处，长期不一致 |
| §7 状态须有暂停与中止态 | 只有运行/等用户/异常/完成四态，用户说「先放一放」或「别做了」无处落 |
| §7 系统瞬态故障自愈不须用户 | 异常态只能用户放行，无人值守时网络抖动即死锁 |
| §7 状态文件按会话隔离 | 两个会话共用同一份状态文件，目标被对方整份覆盖 |
| §7 审计行须带写入方会话 | 只看文件名无法区分「谁写的」，B 会话写 A 会话的文件时记录会被归错 |
| §7 状态文件只许按字段改 | 整文件重写把正在等用户决策的目标与 accept 一起覆盖 |
| §7 恢复会话须固定顺序 | 恢复时可能不重读主文件、不校验状态文件、不看是否过期 |
| §7 重派总次数须有单一数据源 | 按成员 `retry_count` 累加，换成员后总数丢失 |
| §7 凭据需求由写入路径派生 | 凭据四值混了「路径」与「是否需凭据」两个维度，同一情形有两种填法 |
| §7 合法缩减与截断须区分 | 截断护栏只看字节数，状态文件目标切换后按规范归档再缩短的合法文件被同一判定拦下 |
| §7 受保护判定以写前为准 | 不写明判定时点则首次创建是否算破坏性两种读法并存 |
| §7 同一术语不得指两个命令 | 都叫「定基线」，一个指全项目快照、一个指单文件字节行数，取错则取证无效 |
| §7 运行期文件须落项目目录 | 审计日志与基线文件写在模板目录，而内容记录的全是项目路径，路径与内容不一致 |
| §8 实质与流程分开判定 | 流程小瑕疵被判成实质失败，任务无限续跑 |
| §8 完成与合规须分开表达 | 只有完成态，流程不合规时无法表达「做完了但不合规范」 |
| §8 清理与破坏性分界 | 既有未跟踪文件与本轮临时目录混在一批待办里，差点误删 |
| §9 数值只在阈值表 | 同一阈值在正文、模板、其他文件各写一遍，改一处漏两处 |
| §9 规范通用 | 规范里写死项目路径、具体会话文件名与平台坑，换项目即失效 |
| §9 改规范同步模板 | 主文件改了，模板仍是旧口径，执行时按模板走 |
| §2 交付前全量自检 | 每轮只修上一轮列出的问题，改完又冒新问题 |
| §9 重派分类上限可覆盖 | 单次超时/假完成/静默超时属可处理项，若一并锁死则 Lead 无法自行重试；安全底线改由不可覆盖的重派总上限承担 |
| §1 目标切换先归档 | `state=waiting_user` 时整体重写状态文件，正在等用户决策的目标与 accept 被抹掉 |
| §1 判据不得重复 | accept 第 3、4 条判据相同，x/y 计数失真 |
| §3 SCAN 表不替代简报 | 把 SCAN 表当成汇报，SCAN 完成后未出简报，用户两次追问 |
| §5 派发须列连带文件 | 任务书只写改正文，未列被测试断言的配套测试文件 |
| §5 派发前取基线 | 未先跑验收命令取基线，改动后才发现改前就是红的，无法区分新旧 |
| §5 写域外红点处置 | 验收红点落在他人写域，成员既不完成也不释放，任务空占 in_progress 一轮 |
| §5 只读侦察含日常命令 | 以「只是看一眼」为由自行跑 git status、列目录、看 mtime，绕过授权 |
| §4 等成员只豁免动作计数 | 把「等成员期间不计」读成「不用出声」，长时间静默，用户不知进展 |
| §1 成员结论须标未验证 | 把成员回报的结论性断言当成已核验事实写进报告 |
| §3 可独立验证须有定义 | 只核写域不重叠就并行，任务验收被他人写域红点污染 |
| §4 未声称完成不等于假完成 | 认真做一半被记为假完成，据错误类型多算重派次数 |
| §5 写域外红点可机械证明无关 | 一律上升用户决策，本可 deselect 取证的正常交付被卡一轮 |
| §5 成员临时文件放仓库外 | 成员在仓库根建临时目录，被未跟踪文件守护扫成红点 |
| §5 跨任务约束须广播 | 一个成员踩到门禁锚点，未广播给其他成员，同样的坑再踩一次 |
| §5 拆细判据 | 平台不提供上下文用量，超限治理手段失效，无法判断是否该拆细 |
| §9 重派须有定义 | 把追加要求也算一次重派，口头宣布已达上限，差点误触发熔断 |
| §9 连续失败按错误类型 | 同一子任务不同错误类型被合并计数，提前熔断 |
| §9 规范变更不追溯 | 执行中规范改了三次，已完成的动作被新条款判为违规 |
| §4 记录类型须指定对话块 | 检查点类记录只写「必须同轮出简报」，未指定具体块类型 |
| §4 同轮多检查点可共享块 | 自检把「每条记录一个块」写成「一一对应」，同一轮完成派发与验收两项检查点时永远判失败 |
| §4 未派发任务的三项自检写不适用 | 派发四要素、派发前基线、拆细判据只对已派发任务成立 |
| §9 同子任务连续瞬态额度独立计 | 一次执行把瞬态重派算到总上限之外的独立额度里 |
| §9 无降级模型处理规则 | 平台无降级模型时该额度悬空，执行者各自解释 |
| §4 定时汇报类型取值 | 「定时汇报」行写「类型」，取值范围未定义 |
| §5 主规范不得绑定具体测试框架 | 主规范写死 pytest 专有参数 `--deselect` |
| §6 受版本管理文件不得整文件覆盖 | 执行者把自己写的日志判成「内务」，用整文件重写把 52K 日志截断成 1.1K |
| §6 破坏性判定与动机无关 | 同一覆盖行为，按「是不是我的过程记录」解释一次，按 `git ls-files` 解释一次，结论相反 |
| §7 状态文件不适用凭据要求 | 状态文件每检查点必须整文件覆写，与「受版本管理文件替换须用户凭据」直接冲突 |
| §7 凭据来源取值须定义 | 自检要求凭据来源等于某值，主规范只写「凭据来源」不写取值范围 |
| §7 凭据存在性只能靠审计证明 | 环境变量一旦设置就长期存在，事后无法区分「本次写入前设的」与「上次设过的」 |
| §7 受保护写入须凭据 | 判断口与审核口都在执行者手里，自检查不出「会不会不做」 |
| §5 空字段须写明未填写时的退路 | 新增字段留空时主规范无退路，红点取证路径悬空 |
| §1 执行范围不得自行扩大 | 用户只要求删一个文件，执行者自行升级为「删文件 + 改测试 + 跑基线 + 跑全量」 |
| §7 尚未建文件的追加须先判存在 | 追加操作对不存在的文件直接读取，抛 `FileNotFoundError` |
| §7 运行期文件须入忽略清单 | 审计日志与基线文件放项目根后恒为未跟踪，自检每次都会把它们当成多出项 |
| §7 状态文件判定不得只看后缀 | 任何 `foo_*_PROGRESS.md` 都被当成状态文件免凭据，等于给了绕过凭据的后门 |
| §7 归档文件须先核身份 | 只核归档文件存在且含旧内容，未核它本身是状态文件 |
| §7 两份校验脚本的判据须一致 | 两处比字节/行，一处比字节/行/节，同一文件两个结论 |
| §7 脚本定位不得两套基准 | 一处用当前目录、一处用项目根，在子目录跑时两者不一致 |
| §5 主规范描述行为而非手段 | 主规范正文写具体脚本名与开关，换实现即失效 |
| §7 受保护写入步骤不绑定工具 | 写入路径的说明里夹带命令行开关，读者以为规范只对该工具成立 |
| §9 模板示例不得写具体命令 | 报告模板验收命令示例写死某解释器调用方式 |
| §7 校验装置须兼容注释 | 模板 yaml 块自带行尾 `#` 注释，校验脚本不剥注释 |
| §7 迁移旧运行期文件须先确认项目目录 | 迁移逻辑无条件执行，在子目录里跑会把旧文件搬到错处 |
| §5 Lead 禁止项限于业务对象 | 原措辞把验收、汇报、落盘也算执行，与元任务豁免自相矛盾 |
| §9 阈值表项名须与覆盖表一一对应 | 覆盖表一行含四类错误，阈值表四行，无法逐行对应 |
| §2 轻量模式 | 用户只问一句也要建状态文件、出三行、走全流程 |
| §1 场景到必读文件须为硬规则 | 只说「按索引触发时读」，实际可整轮不读任何模板 |
| §7 自检诚实性须显式声明 | 自检由执行者自己跑，无外部校验，不声明则报告里的「已验证」无边界 |
| §6 破坏性判定须可机械执行 | 判据写成「用户会不会问」，同一操作不同人得出不同结论 |
| §7 整文件重写不等于语义整文件替换 | 编辑器保存整文件被一律判为破坏性，改一行代码即需用户凭据 |
| §6 安全阈值授权口径须统一 | 一处写「用户安全授权」、一处写「明确书面授权」 |
| §9 规范变更须有跨会话台账 | 会话私有日志记 `spec-change` 后其他会话看不到 |
| §9 台账与日志两处各自缺一即失败 | 只记日志不记台账，跨会话仍看不到；两处格式不同又无判定依据 |
| 文档写作 · 原则八 独立成节 | 文档边写边想，先写的节过长后写的节被压缩；示例命令从未跑过就写进文档 |
| SKILL 去项目侧 | SKILL 内出现具体项目文件名与会话文件名，跨项目复用时必改 SKILL 本体 |
| 打包为 SKILL | 11 个文件散落项目根，跨项目复用靠复制粘贴 |
| 去掉脚本 | 两个 `.py` 装置随规范分发，跨项目各存一份、版本同步靠人 |
| 项目根三文件制 | 项目根曾出现 `extensions.md`、`.safe-write.log` 等额外文件 |
| 模板加完整示例 | 模板只有字段清单与占位符骨架，新读者打开看不懂最终输出长什么样 |
| 8 原则照搬进项目入口 | 首版把 8 原则「融合」进 SKILL.md，第一原则被压成四条自检，丢失「判断标准只有一条」与「冗余观察 / 过度代理」两个命名；用户指出「我给你的第一原则放哪去了」 |
| SKILL 只留机制，原则进 AGENTS.md | 8 原则若放 SKILL 里，纯咨询不加载 SKILL 的那一轮原则就不生效；原则应常驻，机制可按需加载 |
| 示例标注示意 | 模板示例原写成看似真实的路径、sha16、命令输出，违反原则五「不编造」；改为在示例段开头标注「以下为示意」 |

## 当前维护记录

### 2.0.0：可移植入口与按需执行

本次针对实际文档缺陷整改：

- 项目只复制 AGENTS.md，Skill 作为完整目录独立安装；不再假设项目内存在 Skill 相对路径，不承诺未经实测的自动发现。
- 删除特定平台会话变量、项目附录与“根目录只能三个文件”的依赖；会话身份可安全生成并恢复，运行记录与分发资源分离。
- 以 light / standard / team 适配工作规模，保留目标、判据和证据，取消强制团队、人工汇报计数与自引用哈希台账。
- 状态 schema、阈值只由主文件定义，九份模板和自检同步；模板示例不作为实测证据。
- Lead 可执行和集成；原失败保留，排除测试只能诊断；自检完成不代表用户验收。
- 保留下面原稿历史供追溯，不再执行其中已被现行规则取代的要求。当前版本的实际改动以 Git 历史为准。

### 2.0.1：隔离场景验证发现的修正

以下为本次实际验证发现，区别于上方未独立核实的原稿历史：

- 多阶段试跑未在实现前对话输出 SCAN：明确 S/C/A/N 的可见输出和时机，模板、自检同步。修订后的独立任务已观察到实现前输出，仍不代表所有模型均可靠遵循。
- PyYAML 解析发现状态示例时间变成日期对象：对时间加引号。另一次试跑的含冒号列表项被解析成映射：补安全序列化与解析回读要求，不能仅凭回读文本宣称字段类型正确。
- 缺依赖示例容易把环境异常直接转为请求许可：区分原授权内可逆修复与确需新授权的共享环境变更。
- 故障注入与时间/成员模拟须分别报告；保留首次违规事实，不用补记录追溯宣布当时合规。试跑曾把模拟重派数混入真实 `retry_total`，已按现有字段定义纠正，命令重试和模拟事件不能作为真实重派。
- 验证脚本初版静默跳过解析错误/非围栏状态，扩大覆盖后发现两处未加引号时间；收紧为指定状态必须解析、错误必须失败，并保留原始失败快照。

### 2.0.2：第二轮边界审阅与可执行性澄清

- 最小原则的行为探针覆盖有限样本：咨询未读文件，定向读取避免无关全仓探查，局部修改先读目标区段，必要断言实际运行；发现“无关探查”的判定需结合是否改变决策，不能把少工具调用本身作为目标。
- 第一原则补充读取范围锚点、尊重工具强制前置条件和拒绝、用户点名的安全授权检查不能静默省略，以及成本/范围超授权时先说明并澄清。
- 修订 Skill 与对应模板：针对明确项目任务，项目隔离、可逆本地依赖安装可在已有授权内；共享/全局变更或新权限需授权。常规清理默认仅清理任务产物，但用户明确点名既有删除目标可按该目标授权，仍核实身份、范围与不可逆后果。
- 本轮未执行真实删除、依赖安装、用户拒绝读取后的写入或高成本全量检查；上述规则是静态审阅修正，需另行在安全隔离环境做行为回归。平台自动发现、失败成员重派和跨模型兼容仍受环境限制。
